# Visual Bottleneck 진단 실험 (WorldMM, EgoLifeQA A1_JAKE)

> **한 줄 요약.** WorldMM에서 시각 정보는 쓸모가 있는데, 메모리가 그것을 찾아오지 못한다. 그리고 그 원인은 시각
> 메모리를 만드는 방식에 있다. **텍스트 메모리는 여러 단계의 LLM 전처리로 개체·관계·시간 스케일을 구조화하지만,
> 시각 메모리는 30초 클립마다 벡터 하나를 만들 뿐이다.**
>
> - 정답 구간의 프레임을 직접 주면 답이 좋아진다: D−B **+7.2 %p**(3회 평균, 3회 모두 양수), 텍스트 검색이 target을
>   놓친 82문항에서는 **+13.0 %p (p=0.010)**. 모델은 시각 근거를 쓸 줄 안다(utilization은 병목이 아님).
> - 하지만 실제로 검색된 프레임은 거의 도움이 안 된다: 원본 WorldMM(E−B) **+0.9 %p**, visual 검색을 강제해도(E′−B) **+1.7 %p**.
> - 같은 120문항에서 텍스트 검색은 **38~56문항**에서 target 시점을 가져왔지만, visual 검색은 **6문항(5%)** 이었다.
> - 즉 병목은 **retrieval**이고, 그 뒤에는 **시각 메모리의 가공 부족**이 있다. 시각 쪽에도 텍스트처럼 구조화된 추출이
>   필요하다. 다음 실험 [`../gaze_crop`](../gaze_crop/README.md)은 그 첫 단계로 가장 단순한 처리(자르기)부터 검증한다.

설계 전문은 [`PLAN.md`](PLAN.md), 숫자 원본은 [`analysis/seeds_summary.md`](analysis/seeds_summary.md)(3회 평균)와
[`analysis/summary.md`](analysis/summary.md)(1회차)에 있습니다.

---

## 1. 왜 이 실험을 했나

### 1.1 질문: visual 메모리의 이득은 왜 작은가

WorldMM 논문은 episodic + semantic 메모리에 visual 메모리를 더하면 성능이 오른다고 보고합니다(E+S < E+S+V).
하지만 **오르는 폭이 작습니다.** 이유는 서로 다른 두 가지일 수 있고, 어느 쪽이냐에 따라 고칠 곳이 다릅니다.

| 가설 | 뜻 | 맞다면 고칠 곳 |
|---|---|---|
| **Retrieval 문제** | visual 메모리가 정답에 필요한 클립을 찾아오지 못한다 | 시각 메모리를 만들고 검색하는 방식 |
| **Utilization 문제** | 정답 클립을 줘도 응답 모델이 시각 근거를 활용하지 못한다 | 모델 입력 |

논문 설정 그대로는 둘이 섞여 있습니다. 그래서 **검색을 완벽하게 대체한 조건(oracle visual)** 을 만들어, 검색이
성공했다면 얻었을 이득과 실제로 얻은 이득을 나란히 비교했습니다.

### 1.2 배경: 텍스트와 시각 메모리는 만드는 방식이 전혀 다르다

WorldMM 파이프라인을 따라가 보면 두 메모리에 들인 가공의 양이 크게 다릅니다.

| | 텍스트 메모리 (episodic + semantic) | 시각 메모리 |
|---|---|---|
| 입력 가공 | 중국어 캡션·자막 → 번역 → 자막 동기화 → 1인칭 재작성 → **30초 / 3분 / 10분 / 1시간 요약** (모두 GPT-5-mini) | 30초 클립에서 **16프레임 균등 샘플링** |
| 정보 추출 | 캡션 7,701개마다 **개체(NER)와 관계(triple)** 추출. semantic triple을 따로 뽑아 시점별로 통합 (623개 시점) | 없음 |
| 저장 구조 | 스케일별 개체·사실 그래프. 30초 스케일만 **개체 46,897개, 사실 84,874개** | 클립마다 **VLM2Vec 벡터 1개** (6,223개) |
| 검색 | 그래프 + PPR, 4개 스케일에서 후보를 모아 LLM이 필터링. 에이전트가 여러 라운드 반복 | 질문과 cosine 유사도 top-3 |

텍스트는 "무엇을 남길지 고르고(요약), 무엇이 있는지 뽑고(개체·관계), 여러 시간 단위로 정리(스케일)"하는 과정을
거칩니다. 시각은 그런 과정 없이 원본 프레임을 통째로 벡터 하나에 압축합니다. 이 실험의 결과를 이 차이에 비춰 읽습니다.

## 2. 실험 설계

### 조건

| 조건 | 입력 | 역할 |
|---|---|---|
| **A** | 질문만 | 사전지식 / 찍기 기준선 |
| **B** | 질문 + 텍스트 메모리 (episodic + semantic, visual 끔) | 논문의 E+S |
| B_replay | B가 저장한 텍스트 컨텍스트로 최종 답만 다시 생성 (검색 없음) | B의 답 생성 반복용. 프롬프트가 B와 같아서 B의 1회차가 B_replay의 1회차 |
| **C** | 질문 + oracle 프레임 | 시각 근거만으로 풀 수 있나 |
| **D** | 질문 + B의 텍스트 컨텍스트 + oracle 프레임 | 텍스트가 있을 때 시각 근거가 더해 주는 것 |
| **E** | 원본 WorldMM (에이전트가 visual 검색 여부를 스스로 결정) | 논문의 E+S+V |
| **E′** | B의 텍스트 컨텍스트 + 질문으로 강제 검색한 visual top-3 | 텍스트를 고정하고 visual만 검색 결과로 바꾼 통제 비교 |

- **Oracle 프레임**: 문항의 `target_time`이 들어가는 30초 클립에서 1 fps로 뽑은 프레임(최대 64장, 평균 32.7장).
  모든 조건이 디스크에 캐시된 같은 JPEG를 씁니다.
- **텍스트 고정**: B를 한 번 돌려 문항별 검색 결과를 `text_context/{qid}.json`에 저장하고, D와 E′가 그대로 재사용합니다.
  그래서 D−B와 E′−B는 순수하게 visual을 더한 효과입니다.
- **반복 실행**: 응답 생성이 샘플링(Qwen3-VL 기본, temperature 0.7)이라, 답을 한 번 생성하는 조건(A, B_replay, C, D,
  E′)은 **3회**(1회차 + 시드 1, 2) 돌려 평균을 냈습니다([`run_seeds.sh`](run_seeds.sh), [`analyze_seeds.py`](analyze_seeds.py)).
  에이전트 루프를 도는 B와 E는 1회입니다. 텍스트는 1회차 검색 결과로 고정했으므로, 반복은 답 생성의 무작위성만 평균 냅니다.
- **검정**: 같은 문항끼리 짝지은 비교입니다. 3회 평균은 문항별 평균 점수 차이에 부호 뒤집기 순열 검정, 1회 비교는
  exact McNemar(모두 양측)를 썼습니다.

### 모델과 메모리 (WorldMM-8B 설정)

| 구성요소 | 모델 | 출처 |
|---|---|---|
| Episodic OpenIE (30초 / 3분 / 10분 / 1시간) | GPT-5-mini | 30초는 저자 배포본, 나머지는 [`build_episodic_cache.py`](build_episodic_cache.py)로 생성 |
| Semantic 메모리 | GPT-5-mini | 저자 배포본 |
| Visual 임베딩 | VLM2Vec-V2.0 | 저자 배포본 |
| 검색 에이전트 / 응답 모델 | Qwen3-VL-8B-Instruct (한 인스턴스 공유) | 로컬 |

3분·10분·1시간 OpenIE는 배포본에 없어서 GPT-5-mini로 새로 만들었습니다. Qwen으로 만들면 1시간 캡션(평균 9,588자)에서
같은 단어를 반복하다 JSON이 깨져 67%가 빈 개체로 저장됐고, GPT-5-mini로는 0%였습니다.

### 데이터

A1_JAKE 500문항 중 oracle을 정의할 수 있는 478문항에서 **유형당 24개씩 120문항**을 층화 추출했습니다(유형 ×
`need_audio` × 질문–target 일수 간격). `need_audio=False`(시각 근거) 70개, `True`(대화 근거) 50개입니다.

### 3.1 정확도

| 조건 | 설명 | 회차별 (1회차 / 시드1 / 시드2) | **평균** | 표준편차 | 회차 간 답이 바뀐 문항 |
|---|---|---|---|---|---|
| A | 질문만 | 29.2 / 28.3 / 30.8 | **29.4** | 1.3 | 9 / 120 |
| B (B_replay) | 텍스트 메모리 | 40.8 / 43.3 / 45.0 | **43.1** | 2.1 | 10 / 120 |
| C | Oracle 프레임만 | 36.7 / 36.7 / 39.2 | **37.5** | 1.4 | 9 / 120 |
| **D** | **텍스트 + oracle 프레임** | 50.0 / 50.8 / 50.0 | **50.3** | 0.5 | 4 / 120 |
| E′ | B 텍스트 + 검색된 visual (강제) | 45.8 / 44.2 / 44.2 | **44.7** | 1.0 | 9 / 120 |

샘플링 노이즈는 작습니다(표준편차 0.5~2.1 %p, 회차 간 답이 바뀐 문항 4~10개).

| C − A | 시각 근거만으로 도움이 되나 | +7.5 | **+8.1** | +7.5 / +8.3 / +8.3 | 24 / 17 | 0.074 |
| **D − B** | **텍스트 위에 oracle visual이 더하는 것** | +9.2 | **+7.2** | +9.2 / +7.5 / +5.0 | 23 / 11 | 0.083 |
| C − B | 어느 modality가 더 쓸 만한가 (진단용) | −4.1 | **−5.6** | −4.2 / −6.7 / −5.8 | 26 / 32 | 0.345 |
| **E′ − B** | **텍스트 위에 검색된 visual이 더하는 것** | +5.0 | **+1.7** | +5.0 / +0.8 / −0.8 | 15 / 10 | 0.620 |

"좋아짐 / 나빠짐"은 문항별 3회 평균 점수가 오른 / 내린 문항 수입니다.

### 3.3 시각 근거는 어디서 도움이 되나 (3회 평균)

**텍스트 검색이 target을 놓친 문항에서 효과가 가장 뚜렷합니다.** B가 가져온 캡션 중 10분 이하 스케일의 어느 것도
target 시점을 덮지 못한 문항이 82/120입니다.

| 부분집합 | n | B | D | **D − B** | 좋아짐 / 나빠짐 | p |
|---|---|---|---|---|---|---|
| 텍스트 검색이 target을 놓침 | 82 | 32.9 | 45.9 | **+13.0** | 17 / 4 | **0.010** |
| 텍스트 검색이 target을 찾음 | 38 | 64.9 | 59.6 | −5.3 | 6 / 7 | 0.516 |

즉 시각 정보는 **텍스트 메모리가 놓친 부분을 채울 수 있습니다.** 텍스트가 이미 찾은 문항에서는 더할 것이 없습니다.

| 부분집합 | n | C − A | D − B |
|---|---|---|---|
| need_audio = False (시각 근거) | 70 | **+11.9** (p=0.046) | +8.6 (p=0.123) |
| need_audio = True (대화 근거) | 50 | +2.7 | +5.3 |
| EntityLog | 24 | +15.3 | **+22.2** |
| RelationMap | 24 | +8.3 | +9.7 |
| EventRecall | 24 | +15.2 | −2.8 |
| TaskMaster | 24 | −7.0 | −2.8 |
| HabitInsight | 24 | +8.4 | +9.7 |
| gap 0 (당일) | 57 | +5.9 | +0.6 |
| **gap 1 (하루 전)** | 33 | +15.1 | **+17.2** |
| gap 2+ | 30 | +4.4 | +8.9 |

유형별·gap별 칸은 24~57문항이라 p값 없이 방향만 봅니다.

### 3.4 검색 진단: 텍스트는 찾고, 시각은 못 찾는다

**같은 120문항에서 두 메모리가 target 시점에 닿은 비율**

| 메모리 | target 시점을 가져온 문항 |
|---|---|
| 텍스트 (B), 30초 캡션만 | 19 / 120 (16%) |
| 텍스트 (B), 10분 이하 스케일 | 38 / 120 (32%) |
| 텍스트 (B), 전체 스케일 | 56 / 120 (47%) |
| **시각 (E′), top-3 클립** | **6 / 120 (5%)** |

텍스트 쪽은 여러 라운드·여러 스케일에서 후보를 모으므로 조건이 같지는 않습니다. 하지만 같은 30초 단위만 비교해도
16% vs 5%이고, 그 차이가 3.2에서 **텍스트는 +13.7 %p(B−A), 검색된 visual은 +1.7 %p**라는 기여 차이로 이어집니다.

**visual 검색의 두 가지 실패**

| | E (에이전트 자율) | E′ (강제 호출) |
|---|---|---|
| visual 검색을 한 문항 | **2 / 120** | 120 / 120 |
| target 클립이 top-3에 든 문항 | 0 / 2 | **6 / 120** |
| 정확도 (B 대비) | 41.7 (+0.9, 1회) | 44.7 (+1.7, 3회 평균) |

- **라우팅**: E에서 에이전트는 visual 검색을 120문항 중 2문항에서만 불렀습니다. JSON 파서를 느슨하게 해도 그대로였고
  (`results_robust/E.json`), 나머지 380문항에서도 3/380이었습니다(`results_rest/E.json`, 정확도 44.2%).
- **검색 품질**: 강제로 불러도 target 클립은 5%만 top-3에 들어왔습니다. 그래서 같은 텍스트에 oracle 프레임을 넣으면
  +7.2 %p인데 검색된 프레임은 +1.7 %p입니다. 텍스트 검색이 실패한 82문항에서도 E′−B는 +5.3 %p(p=0.094)로, 같은
  문항의 oracle(+13.0 %p)에 크게 못 미칩니다.

> 1회차만 봤을 때는 E′−B가 +5.0 %p여서 "target을 못 찾아도 근처 시각 맥락이 돕는다"고 해석했습니다. 3회 평균에서는
> +1.7 %p로 줄고 회차별로 음수도 나와서 이 해석은 철회합니다.

**정답 클립 정의.** recall은 검색된 클립이 `target_time`을 포함하는 30초 클립과 같은지로 셉니다([analyze.py](analyze.py)).
gaze_crop의 시점 기준 정의(`target_spans()`, tol=0)로 다시 계산해도 120문항에서는 결과가 같습니다(E′ 6/120, E 0/2).
22문항은 target 시점이 클립 경계에서 3초 이내라 바로 옆 클립도 오답으로 칩니다. 그래서 5%는 엄격한 값입니다.

### 3.5 텍스트 검색 쪽 진단 ([`dpr_recall.py`](dpr_recall.py))

텍스트 검색의 한계도 확인했습니다. 에이전트가 낸 episodic 질의를 그래프·PPR·LLM 필터 없이 **같은 텍스트 인코더의
단순 cosine**으로 30초 캡션에 다시 돌렸습니다(episodic 질의가 있었던 96문항).

| 검색 방식 | 30초 target 적중 |
|---|---|
| HippoRAG (그래프 + PPR, top-10) | 34 / 96 |
| 단순 cosine, 에이전트 질의 | @3 22 · @10 33 · @50 51 · @100 55 |
| 단순 cosine, 질문 원문 | @3 20 · @10 37 · @50 51 · @100 56 |
| 단순 cosine, target 캡션 자신 (sanity) | 96 / 96 |

top-10에서 그래프와 단순 cosine이 비슷합니다(34 vs 33). 텍스트 검색도 완벽하지 않고 질의·인코더가 한계입니다. 다만
텍스트는 이 30초 캡션 위에 3분·10분·1시간 스케일이 더 있어서 전체로는 절반 가까이 target에 닿습니다(3.4).

## 4. 해석

PLAN.md 1장의 판정표에 대입하면:

| Oracle visual gain (D−B) | Retrieved visual gain (E−B / E′−B) | 판정 |
|---|---|---|
| **+7.2** (3회 모두 양수, p=0.083) · 텍스트 실패 문항 **+13.0** (p=0.010) | **+0.9** (1회) / **+1.7** (3회, p=0.62) | **큼 / 작음 → retrieval bottleneck** |

1. **시각 정보는 쓸모가 있고, 모델은 그것을 쓸 줄 압니다.** 정답 프레임을 주면 시각 근거 문항에서 +11.9 %p(프레임만,
   p=0.046), 텍스트 검색이 놓친 문항에서 +13.0 %p(p=0.010), 하루 전 사건에서 +17 %p가 오릅니다. utilization은 병목이
   아닙니다.
2. **병목은 retrieval이고, 두 층입니다.**
   - (a) **라우팅**: 에이전트가 visual 검색을 거의 부르지 않습니다(2/120, 3/380).
   - (b) **검색 품질**: 불러도 target을 거의 찾지 못합니다(5%). 그래서 검색된 visual의 기여는 +1.7 %p에 그칩니다.

   (a)를 없앤 E′에서도 (b) 때문에 이득이 없으므로, (b)가 더 근본적인 문제입니다.
3. **검색 품질이 나쁜 이유는 시각 메모리의 가공 부족에 있다고 봅니다.** 같은 문항에서 텍스트 메모리는 target 시점에
   16~47% 닿고 정확도를 +13.7 %p 올리는데, 시각 메모리는 5%에 +1.7 %p입니다. 두 메모리의 차이는 1.2절의 표 그대로입니다.
   텍스트는 요약·개체 추출·다중 스케일·그래프를 거친 반면, 시각은 클립당 벡터 하나입니다. 30초 동안의 장면을 벡터 하나로
   평균하면 질문이 묻는 특정 물체나 순간이 배경에 묻힙니다. gaze_crop 실험에서 **픽셀을 자르기만 해도 visual recall이
   상대 46% 오른 것**이 이 해석을 지지합니다.
4. **Text dominance는 뚜렷하지 않습니다.** C−A(+8.1)와 D−B(+7.2)가 비슷해, 텍스트가 있어도 시각이 더해질 여지가 있습니다.
5. **시각이 도울 수 있는 범위에는 한계가 있습니다.** 대화 근거 문항에서는 oracle 프레임만으로 +2.7 %p이고, EventRecall과
   TaskMaster는 D−B가 −2.8 %p입니다. 시각 메모리를 개선해도 이 구간은 오르지 않습니다.

**결론과 방향.** 시각 메모리도 텍스트처럼 **구조화된 추출**을 거쳐야 합니다. 텍스트 파이프라인의 각 단계에 대응하는 시각
쪽 처리를 하나씩 붙여 검색이 어떻게 달라지는지 보는 것이 다음 순서입니다.

| 텍스트에서 하는 처리 | 시각 쪽 대응 | 상태 |
|---|---|---|
| 요약: 무엇을 남길지 고른다 | 영역 선택(crop), 프레임 선택(fixation) | 자르기 완료 ([gaze_crop](../gaze_crop/README.md)), fixation 제안 |
| 다중 시간 스케일 | 주목 구간별 벡터, 여러 시간 단위 | 제안 (gaze_crop 5.3) |
| 개체·관계 추출 (NER, triple) | 사람·물체 검출, 개체 단위 시각 표현 | 미착수 |
| 그래프 + PPR | 개체 기반 시각 인덱스, 텍스트 그래프와 연결 | 미착수 |

라우팅 문제(a)는 이와 별개로 프롬프트나 호출 정책에서 다뤄야 합니다. 그 전까지 시각 메모리 개선의 효과는 E가 아니라
**E′ 기준**으로 잽니다.

## 5. 한계와 주의사항

- **표본이 작습니다.** n=120이면 5 %p가 문항 6개입니다. p<0.05는 부분집합 결과(텍스트 실패 82문항의 D−B, 시각 문항의
  C−A)이고, 전체 D−B(0.083)와 D−E′(0.089)는 경계선입니다. 방향은 3회 모두 일관됩니다.
- **"가공 부족이 원인"은 해석입니다.** 이 실험이 직접 보인 것은 "시각 정보는 쓸모 있는데 지금의 시각 메모리로는 찾지
  못한다"까지입니다. 구조화된 시각 추출이 실제로 검색을 크게 올리는지는 앞으로 검증할 가설이고, 지금 증거는 가장
  단순한 처리(자르기)의 효과뿐입니다.
- **텍스트와 시각의 검색 조건이 같지 않습니다.** 텍스트는 여러 라운드와 스케일에서 후보를 모으고, 시각은 한 번에 top-3입니다.
  3.4의 비교는 "현재 파이프라인 그대로"의 비교입니다.
- **반복은 답 생성만 평균 냈습니다.** 텍스트는 1회차 검색 결과로 고정했고, B와 E는 1회 실행입니다.
- **120문항 subset은 visual 검색이 유난히 어려운 표본일 수 있습니다.** gaze_crop 3.6절에서 같은 검색기로 나머지 380문항을
  채점하니 recall이 이 120문항보다 훨씬 높았습니다. "recall 5%"는 이 subset의 특성이 섞인 값입니다.
- **피험자 1명, 응답 모델 1개(Qwen3-VL-8B).** 큰 모델에서는 라우팅 행태가 다를 수 있습니다.
- **D와 E′의 프레임 수가 다릅니다.** D는 평균 33장, E′는 중앙값 63장입니다.
- **Episodic 캐시 출처가 섞여 있습니다.** 30초는 저자의 결과, 나머지는 우리가 GPT-5-mini로 만든 결과입니다. 모든 조건이 같은
  캐시를 쓰므로 조건 간 비교는 유효합니다.
- **Exp.3(visual masking)은 아직 돌리지 않았습니다.**
- **결론에서 제외한 실행**
  - `results/B_leaky.json` (35.8%): 미리 만들어진 전체 주간 인덱스로 시작해 초반 문항에 미래 캡션이 새어 들어간 실행.
    이후 [`eval_egolife.py`](eval_egolife.py)가 시작할 때 인덱스를 비우도록 고쳤습니다.
  - `results/E_novisual.json` (41.7%): visual 검색이 항상 0프레임을 돌려주던 버그를 고치기 전의 E.

## 6. 다음 실험: [`gaze_crop`](../gaze_crop/README.md)

시각 메모리 구조화의 첫 단계로, **가장 단순한 처리인 "자르기"만 해도 검색이 좋아지는지** 봅니다. 1인칭 영상에는 착용자가
그 순간 보고 있던 곳(eye gaze)이 기록돼 있으므로, 그 주변을 잘라서 임베딩합니다.

| 관찰 (500문항, 6,223클립, recall@3) | 값 |
|---|---|
| 시선 crop vs 전체 화면 | 9.2% → **13.4%** (상대 +46%, p=0.006) |
| 중앙 고정 crop | 10.8%. 시선 crop과의 차이 +2.6 %p (p=0.079), 엄격 채점에서 +0.4 %p |
| 순위 전체 | 시선 crop이 대부분의 측정에서 1위지만, 중앙 crop 대비 이득은 주로 200위 아래 |
| 답 정확도 (E′, 120문항, 각 1회) | 45.0% vs 45.0% (이 120문항은 두 arm 모두 recall ≈ 0.8%) |

**가공을 조금 넣자 검색이 올랐다**는 것이 이 실험의 핵심 결과이고, 1.2절의 "시각 메모리는 가공이 부족하다"는 해석을
뒷받침합니다. 다만 그 이득의 큰 몫은 "어디서 잘랐나"보다 "잘랐다는 사실"에서 나옵니다. 다음 단계로 fixation(시선이 머문
순간)으로 프레임을 고르는 실험과, 클립당 벡터 하나를 주목 구간별로 나누는 실험을 제안했습니다.

## 7. 재현

저장소 루트에서 실행합니다. 전체 절차는 PLAN.md 5장에 있습니다.

```bash
cd ~/WorldMM && source .venv/bin/activate

# 준비 (1회)
python experiments/visual_bottleneck/build_subset.py
python experiments/visual_bottleneck/seed_hipporag_cache.py        # 30초 OpenIE 시딩
python experiments/visual_bottleneck/build_episodic_cache.py       # 3분/10분/1시간 OpenIE (GPT-5-mini, OPENAI_API_KEY 필요)
python experiments/visual_bottleneck/extract_oracle_frames.py

# 조건 실행 (B가 먼저: D, E'가 B의 text_context를 쓴다)
for c in B A C D E E_prime; do
  python experiments/visual_bottleneck/eval_egolife.py --condition $c --resume
done

# 답 생성 반복 (A, B_replay, C, D, E' x 시드 1, 2). results/ 는 건드리지 않음
bash experiments/visual_bottleneck/run_seeds.sh      # -> results_seeds/seed{1,2}/, 끝나면 analyze_seeds.py 자동 실행

# 집계
python experiments/visual_bottleneck/analyze.py        # -> analysis/summary.md (1회차)
python experiments/visual_bottleneck/analyze_seeds.py  # -> analysis/seeds_summary.md (3회 평균)
python experiments/visual_bottleneck/dpr_recall.py     # -> analysis/dpr_recall*.json
```
